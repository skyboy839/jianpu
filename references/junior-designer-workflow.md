# Junior 设计师工作流 / Junior Designer Workflow

本文件展开 SKILL.md 纪律 5 的"Junior 设计师节奏"。核心：**小步暴露，早改比晚改便宜 100 倍**。

## 为什么是"Junior 设计师"而不是"资深设计师"

资深设计师经验充足，能在脑中完成大量设计判断，一次拿出方案即可。Agent 没有这种积累——它更接近一个**有工具、有规范、但缺实战判断**的 junior：能产出，但容易在"理解错了"上翻车。

因此本工作流不是"压低标准"，而是**调整暴露节奏**：把判断点提前暴露给用户，让用户来兜住"理解偏差"这个最大风险。

## 核心节奏：每一步都 show

阶段推进的默认形态是"呈现 → 等反馈 → 推进"，不是"闷头做完 → 交付"。

| 阶段 | show 什么 | 等什么 |
|---|---|---|
| 开工前 | 问题清单（assumptions + unknowns） | 用户批量答复 |
| 骨架 | 灰块占位的布局 | 布局方向确认 |
| 方向 | 3 个 direction-proposal | 用户选 1 |
| 规格 | design-spec.md | 规格确认 |
| 视觉 | 填充后的界面 | 视觉确认 |
| 收尾 | 评审报告 | 交付 |

**硬规则**：不要跳过任何一个 show 点直接推进到下一阶段。用户不在场时，停下来问，而不是替用户做决定。

## 开工前：问题批量暴露

开工前把假设和未知**一次性**发给用户，不要挤牙膏式地一问一停。

格式建议：

```text
在动手之前，我需要确认以下（批量回答即可）：

假设（若无异议我将按此执行）：
- 目标用户是内部运维，不是终端消费者
- 暗色为主模式（团队偏好，来自已读的 tokens）
- 复用现有 Chart 组件，不新引入图表库

未知（需你回答）：
1. 这个仪表盘的核心指标是哪个？——决定视觉焦点
2. 是否需要导出功能？——决定次要操作区
3. 目标 WCAG 级别是 AA 还是 AAA？——决定色板约束
```

**为什么批量**：用户的时间成本是断续的，一次问清比多次打断友好；Agent 也能在一个答复周期内拿到完整上下文，避免来回猜测。

## 骨架：灰块占位先于视觉

视觉细节未定前，先用灰块占位呈现布局，而不是直接上颜色和字体。

```text
┌─────────────────────────────┐
│ [LOGO]        [Search] [User]│  ← 灰块：header
├────────┬────────────────────┤
│ ░░░░░  │  ░░░░░  ░░░░░  ░░░░ │  ← 灰块：sidebar + 3 指标卡
│ ░░░░░  │  ░░░░░░░░░░░░░░░░░ │  ← 灰块：主图表区
│ ░░░░░  │  ░░░░░░░░░░░░░░░░░ │
└────────┴────────────────────┘
```

**为什么先骨架**：布局错了，视觉做得再精致也要推倒重来。先让用户确认"信息摆放对不对"，再投入视觉成本。

## 方向：三方向门的 show 时机

按 `three-directions-gate.md` 产出 3 个 direction-proposal 后，**同时**呈现（不是一个一个给），并明确说明每个方向优化的是什么：

```text
方向 A｜极简主义——优化"一眼看清"，适合专注单任务
方向 B｜信息建筑——优化"信息密度"，适合运维监控
方向 C｜东方哲学——优化"低干扰"，适合长时间驻留

三张截图见附件。请选一个（或说明想组合哪几个的哪些部分）。
```

**不要在用户选择前**继续做视觉细化——方向未定时的细化是浪费。

## 规格：design-spec 的 show 时机

方向选定后产出 design-spec.md，重点是让用户确认**约束和权衡**：

- 硬约束是否正确（品牌色、合规级别、平台规范）。
- 软约束的取舍是否合理（如"团队偏好暗色，所以暗色为主"）。
- anti-slop 的辩护是否成立（如有命中项）。

**此时不展示完整视觉**——design-spec 是"合同"，不是"成品"。

## 视觉：填充后的 show 时机

design-spec 确认后填充视觉。这一步仍要 show，但 show 的是**"规格落地后的效果"**，让用户检查规格有没有被正确执行：

- 色板是否按 spec 用了。
- 字号/间距/圆角是否按 spec 用了。
- a11y 检查（对比度、焦点环）是否通过。

## 收尾：评审报告的 show 时机

按 `review-rubric.md` 产出五维评分 + 硬红线结果，作为交付前的最后一道 show：

```text
哲学一致性： 8/10 — 极简主义约束全部满足
视觉层级：   9/10 — 单一焦点明确
细节执行：   7/10 — 两处字号未用 spec 值（已记入 Fix）
功能性：     8/10 — 键盘路径完整
创新性：     6/10 — 无刻意创新，符合工具定位

Keep: 单一焦点、克制色板
Fix:  [必须修复] 字号偏差 ×2
Quick wins: [≤30min] 焦点环对比度从 3.1:1 提到 4.5:1
```

## 反模式：什么样算"不 junior"

- **闷头做大招**：开工到交付零 show，最后一次性拿出来。
- **挤牙膏提问**：一个一个问，打断用户多次。
- **替用户做决定**：用户不在场时自行假设方向，不记录假设。
- **跳过 show 点**：把骨架/方向/规格的确认合并成一次"最后看看"。
- **只 show 结果不 show 推理**：给截图不给"为什么这样"，用户无法有效反馈。

## 与技术栈无关

本工作流的"show 形态"随栈而异（PyQt 给窗口截图、React 给 Storybook、static 环境给 ASCII），但**节奏不变**：每一步都要 show，等反馈再推进。

## 与 meta-actions 元动作 3 的关系

`meta-actions.md` 元动作 3 定义渐进迁移的**层次顺序**（骨架→视觉→交互→a11y）。本文件定义每个层次**如何 show、何时 show**。两者配合：元动作 3 说"按什么顺序做"，本文件说"每步怎么给用户看"。
