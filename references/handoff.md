# 交付包 / Handoff

多 Agent 协作时，唯一接口是"设计交付包"。按任务类型定义最小集。

## 完整包（全新设计 / restyle）

包含：
- `design-spec.md`（技术中立规格）。
- `tokens/`（三层结构）。
- 三方向对比（direction-proposal 的三个产物）。
- `review-report.md`（五维评分 + 硬红线结果）。
- `appearance-ledger.json` 对应条目。

下游 Agent 必须能仅凭此包完成编码，无需回问设计。

## 精简包（豁免门任务）

包含：
- `before.png` / `after.png`（或 ASCII wireframe 对照）。
- **结构化改动理由**（见下）。
- `token-diff.md`（涉及令牌的差异）。
- `appearance-ledger.json` 对应条目（如涉及）。

**不含**三方向对比。下游 Agent 收到精简包时不得回提三方向，上游已判定豁免。

## 结构化改动理由（精简包专用）

改动理由必须包含以下**四个字段**，缺一即为不合格：

```yaml
reason:
  problem:    "一句话，客观描述问题（如：对比度 3.2:1 低于 AA 4.5:1）"
  solution:   "一句话，说明本改动（如：text.muted 从 blue.400 改为 blue.600）"
  excluded:   "至少 1 个被排除的替代方案 + 为何排除
               （如：改 bg 更深会降低信息密度，与信息建筑派哲学冲突）"
  impact:     "受影响的 token / 组件 / surface 列表"
```

**排除项必填**——防止 Agent 只写"修了对比度"就完事，下游无法判断为何选此方案。

## 精简包的边界

- 精简包**不得用于**任何布局骨架改动、哲学层面新决策、组件契约改动——这些必须走完整包。
- 若下游 Agent 发现改动实际涉及布局/契约，**必须**打回上游重新走三方向门，不得基于精简包自行扩展。

## 与账本的关系

- 完整包必须引用账本条目 id。
- 精简包若涉及 philosophy 变更需引用账本条目；纯缺陷修复可不引用（对应 SKILL.md 纪律 7 的"精简包例外"）。

## 失败模式

- 交付包缺 design-spec → 下游无法理解意图。
- 精简包理由只有 `problem` 和 `solution` → 不可追溯。
- 下游收到精简包后回提三方向 → 违反协议。
- 上游用精简包交付大改动 → 治理失效，评审抽查发现即打回。
